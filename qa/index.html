Q01

自己紹介をお願いします。

竹村直人と申します。10年以上、自営で事業の収支や人材育成に責任を持ち、EC事業では海外のエンジニアと利用者の間に立って、要望を開発の指示へ落とし込んできました。その後、企業のIT基盤を支えるテクニカルサポートを経験しています。

現在は、こうした経験を活かし、AIを使って業務を仕組み化しています。何を作るかだけでなく、そもそも必要な作業か、人とAIがどう役割を分けるかを考えることを大切にしています。

06 / DEVELOPMENT05 QUESTIONS

開発の仕組み

AIの報告を鵜呑みにせず、動かして確かめてから信用する。

Q26

AIを使った開発は、どんな仕組みで進めていますか？

一言でいうと、AIの「できました」という報告をそのまま信用せず、実際に動かして確かめてから次へ進める仕組みです。

1つのAIに全部任せるのではなく、作る役、確かめる役、まとめる役を別々のAIに分けています。確かめる役は、作った側の報告ではなく、自分でテストを動かしたり、アプリを起動して操作したりした結果だけで合否を決めます。AIでは決められないことだけが私に届き、私が判断します。

実際の案件の制作記録を約1分に縮めた動く図を、開発の進め方のページに載せています。

Q26 のリンク ↗
Q27

AIの報告を信用しない、とは具体的にどういうことですか？

「完了しました」「問題ありません」という言葉や、AI同士の合意は、判断の材料にしません。判断に使うのは、テストの実行結果、実行ログ、実際に起動した画面、操作した結果だけです。

そのために、次の関門を順に通ったものだけを次へ渡しています。

  • 作る前に、設計書を別のAI2つが読み、2回続けて合格するまで直す
  • 作ったものは、別のAIが自分でテストを実行し、ログで判定する
  • 部品を組み合わせたら、アプリを起動して最初から最後まで操作する
  • 作ったものは毎回、検査ツールにかけて、書き方の誤りを機械的に洗い出す
  • 最後に、私が自分で触って、目的に合っているか、迷わず使えるかを確かめる

たとえば事業者の届出カレンダーでは、最終検査で「入口に使い方の案内がない」などの指摘が3回の差し戻しでも解消せず、記録と一緒に私へ相談が届きました。私が直し方を決めてから作り直し、再検査で合格して納品しています。

Q27 のリンク ↗
Q28

なぜ、どんな言語でも対応できるのですか？

合否の物差しを「コードが上手そうに見えるか」ではなく、「テストを実際に動かして通ったか」にしているからです。

実行結果で判定するので、言語が変わっても同じ基準で品質をそろえられます。私がすべての言語に詳しいわけではありませんが、動かして確かめる仕組みがあることで、言語ごとの出来の差を抑えています。

Q28 のリンク ↗
Q29

なぜ、早く作れるのですか？ 時間と費用はどのくらいですか？

大きな仕事を小さく分けて、別々のAIが同時に進めるからです。1つ1つの仕事が小さいので間違いも減り、AI同士で直せるものは直します（差し戻しは最大3回）。止まるのは、AIでは決められないことが出たときだけです。

実績を見ると、1件あたりのAIの作業時間はおよそ1〜7時間、AIの利用費用は約2〜75ドルでした。各実績カードのCOSTとAI稼働時間は、実行ログからの実測値です。人が判断する時間や、お客様とのすり合わせの時間は含みません。

Q29 のリンク ↗
Q30

どこまで広げられますか？

仕組みとしては、チームの数を増やすほど同時に進められる作業が増えます。実際に、1つの案件を3〜6チームに分けて並行で作っています。

広げるときに一番大事にしているのは、速さよりも、確かめる仕組みを崩さないことです。起動・本番への反映・最終の承認は人が行う形を変えず、同時に動かす本数を増やしたときにどこまで速くなるかを測りながら広げています。

これから広げたい分野は、大規模な既存システムの改修や長期の保守、スマートフォンのネイティブアプリなどです。初めての分野は、最初にそのことをお伝えし、小さく試してから進めます。

07 / TECH & SAFETY07 QUESTIONS

Q31

コードレビューとテストは、どうしていますか？

作ったAIとは別のAIが、自分の手でテストを動かして確かめます。流れは次のとおりです。

  • 実装役のAIが、機能と一緒にテストも書き、実行した記録を残す
  • 検査ツールで、書き方の誤りを機械的に洗い出す（Pythonは ruff・mypy・bandit、JavaScriptは ESLint と構文チェック）
  • レビュー役のAIが、依頼内容と照らしてコードを読み、テストを自分で実行し直す。実装役の記録と結果が食い違えば、重大な問題として差し戻す
  • 最終検査役のAIが、もう一度テストを独立して実行する
  • チームをまとめたあと、統括検査役がアプリを起動し、画面を最初から最後まで操作して確かめる

どの段階でも、実行できなかった検査は「通った」と書かずに「判定不能」として扱う決まりです。たとえば事業者の届出カレンダーでは、画面担当のレビュー役がテスト308件を自分で実行して全件成功を確認しています。

Q32

どの言語で作るのですか？ それは本当に大丈夫ですか？

言語は、私が書きやすいものではなく、お客様の環境と、納品後に誰が面倒を見るかで選びます。社内のパソコンだけで動かすのか、サーバーに置くのか、既存のシステムや担当の方が使い慣れた言語があるか、を先にうかがいます。

「本当に大丈夫か」は、言葉ではなく確かめた結果でお答えします。どの言語でも、別のAIが自分でテストを実行し、アプリを起動して操作して合否を決めます。納品前の検査ツールが対応しているのはPython・JavaScript / TypeScript・Javaで、それ以外の言語（RubyやPowerShellなど）は、その言語の標準的なテストと書き方のチェックを合格条件に加えて補っています。

作った実績のない言語や構成の場合は、そのことを最初にお伝えします。

Q33

どんな環境で、どういう形で使うのですか？

お客様の使い方に合わせて、次のどれかの形で納めます。

  • 社内のパソコン1台で使う：Windowsのパソコンで、ダブルクリック1回で起動できる形にします。
  • 複数の人がブラウザから使う：Linuxのサーバー（Docker・PM2・Caddy）に置きます。
  • インストールなしで使う：サーバー不要で、ブラウザだけで動く形にします。
  • いまのExcel業務を続けたい：デスクトップ版Excelのまま自動化します。

言語は、Node.js / Express、Python / Flask、TypeScript / React、ブラウザだけで動くJavaScript、Excel VBAで作った実績があります。Google Sheets、n8n、生成AIのAPI（OpenAI・Anthropic）との連携も行っています。

完成品には、起動用のファイルと、何ができるか・使い方・制限事項をまとめた使用説明書を必ず付けます。サーバーに置く場合は、誰が・どこに・何を入力するかを書いた手順書も付けます。

Q34

データベースはどうするのですか？

使う人数と置き場所で選びます。

  • 1台のパソコンや少人数で使う：SQLite。ファイル1つで動き、サーバーの用意がいりません。
  • 複数の人がサーバー経由で同時に使う：PostgreSQL。
  • データベースがいらないもの：ブラウザだけで完結させ、データはお客様の手元に置きます。

データをどこに置き、誰が管理するか（お客様の社内か、クラウドか）は、作る前に必ず決めます。決まっていない場合は、そこを確認事項として明示し、決まるまで本番向けには進めません。

Q35

ハッキングなどへのセキュリティ対策はできていますか？

いま仕組みとして入っているのは、次のことです。

  • パスワード・APIキーなどの秘密情報は、AIに渡さず、コードにも書きません。設定項目の名前だけを置き、実際の値はお客様か私が自分で入力します。
  • 本番環境への接続設定やアカウント作成は、AIにはさせず人が行います。
  • 入力値のチェック、エラー表示で内部情報を出さないこと、秘密情報の置き場所などの確認項目を、チームごとに一つずつ「必要／不要」と理由付きで判定させています。
  • Pythonのコードは、危険な書き方を見つける検査ツール（bandit）に毎回かけています。

一方で、まだ足りていないこともあります。JavaScriptのコードに対する危険な書き方の自動検査、秘密情報の書き込みの自動検出、使っている部品（ライブラリ）の既知の脆弱性の検査、実際に攻撃を試す検査は、いまは入っていません。外部の専門業者による脆弱性診断も受けていません。

これらは開発の仕組みに足す作業を進めています。それまでの間、ログインや個人情報、決済を扱うシステムでは、守る範囲と責任の分担を作る前に決め、必要に応じて専門の診断を受けることをおすすめしています。

Q36

法律や制度が関わる業務も扱えますか？

扱えますが、AIにも私にも、法的な判断はさせない形にします。私は士業ではないため、ツールは判断材料と根拠を示すところまでにして、最終的な判断はお客様や専門家にお任せします。

たとえば雇用契約書のPDFを作るツールでは、法的助言ではないことを画面とPDFの両方に表示し、いつ何を作ったかを記録として残すようにしました。制度の解釈が分かれる点や、AIでは決められない点は、作る途中で私が整理してお客様に確認します。

Q37

納品したあとに手直しが入ったら、どうしますか？

直した部分も、最初と同じ関門をもう一度通します。直したチームが作り直し、別のAIがテストを自分で実行し直し、全体を組み合わせてから、もう一度起動して通しで確かめます。直した箇所だけ見て終わり、にはしません。

事業者の届出カレンダーでも、最終検査の指摘を受けて画面の担当だけを作り直し、そのあと全体の再検査に合格してから納品しました。

レビューや検査の結果は上書きせず、回ごとに番号を付けて残しています。お客様や私が下した判断も記録に残し、次の手直しのときにAIがそれに従うようにしているので、前に決めたことが手直しで崩れることを防げます。

Q38

どんなものなら構築しますか？

決まった手順がある業務を仕組みにするものが得意です。受発注・申請・集計・帳票PDFなどの業務システム、手続きを整理して期限を出すツール、条件を変えて結果を比べるシミュレーター、Excel業務の自動化などです。

一方で、次のものは慎重に進めます。

  • 医療・法律・お金などの最終判断：判断材料を出すところまでにして、決めるのは人という形にします。
  • 個人情報や決済を本番で扱うもの：守るべき範囲と責任の分担を先に決めてから作ります。
  • 要件が言葉になっていないもの：いきなり本番を作らず、先に試作を見ていただいて確かめます。

Q39

ヒアリングは何で、どう行っていますか？

自作のAIチャット「DX導入ヒアリングAI」で、8つの領域を対話形式で聞き取ります。サーバー上で動くWebアプリで、お客様は質問に答えていくだけです。回答は案件の記録にまとまり、そのまま開発の入力になります。

この段階で、今の業務が「誰が・何を・どうしているか」の手順として書けていないと、次へ進まずに止まる仕組みにしています。足りない部分は、私がお客様に直接うかがって補います。
