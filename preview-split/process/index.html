AI開発パイプライン — 複数AIエージェントによる開発組織のシミュレーション

機能ごとに分業する実装エージェントと、 その成果物を検証・承認するレビューエージェント、 全体のチーム編成と最終判断を担う設計統括エージェント―― この3層構成で、実際の開発チームに近いレビュー体制を再現したパイプライン。 要件定義から実装・単体テスト・レビュー（差し戻し）・統合・E2E検証・納品物作成までを自律的に進め、 レビューで解決しない指摘だけを人間へエスカレーションします。 実際の受託案件（食品ギフト仲介事業者向け・受発注管理システム）を このパイプラインで構築し、納品まで完了させました。

01 · CONCEPT

クライアントへのヒアリング内容をもとに、バックエンド（機能別の実装チーム）から フロントエンド（Web UI構築）まで、その案件に必要な役割分担を「設計統括エージェント」が 都度設計する動的なチーム編成を採用。固定の組織図はなく、 レビューの過程で追加の処理が必要と判断されれば、 その場で新しいチームを編成し直すこともあります。

編成された各チームの成果物は「レビューエージェント」が検証し、 最終的な統合判断は設計統括エージェントが行います。 「誰が作ったか」ではなく「実機で動くか」を実際にコマンドを実行して検証してから 承認する、というルールを徹底しています。

指摘に対する差し戻しは最大3ラウンドまで。 それでも解消しない場合は自動的に人間へのエスカレーションに切り替わる 設計で、実際に「テストコードが依存関係の変更に追従できていない」という 指摘が3ラウンド未解消のまま人間判断に回された記録が残っています。

パイプライン起点の要件ヒアリング自体も自作のAIチャットアプリ 「DX導入ヒアリングAI」で行っており、9つの領域の対話ヒアリングを通じて 案件カルテを自動生成し、設計統括エージェントへのインプットとして渡しています （詳細は実績「DX導入ヒアリングAI Webアプリ」参照）。 聞き取る内容と実際の質問を見る →

02 · PIPELINE
要件ヒアリング → チーム編成設計（設計統括エージェント）
バックエンド実装（機能別チーム） → レビュー（レビューエージェント）
承認 / 差し戻し（最大3回） → 追加チーム編成（必要時）
バックエンド結合・E2E検証 → フロントエンド（Web UI）構築
統合判定（設計統括エージェント） → 納品物生成（デモ・説明書・手順書）
人間の最終確認・エスカレーション対応
AI処理 人間の判断 データ / 検証対象
03 · TEAM FORMATION（案件ごとに動的編成されるチーム構成）

チーム名・チーム数はあらかじめ固定されておらず、 ヒアリング内容から設計統括エージェントがバックエンド（機能別の実装チーム）から フロントエンド（Web UI構築）・最終統合まで案件ごとに設計します。 以下は今回の案件（食品ギフト仲介事業者向け）で実際に編成された体制の例です。

BACKEND — 機能別の実装チーム（6チーム）
受注メモ解析
order_memo_parser.py
FAX・LINE等で届く自由文の注文メモをAIが読み、 届け先ごとの下書きに分解。最終確認は必ず人が行う設計。
受注入力
order_entry.py / tracking_entry.py
購入者・複数届け先の受注登録と、配送伝票番号の入力・状態管理を担当。
発注書PDF生成
purchase_order_pdf.py
生産者ごとに発注書PDFを自動生成。PDF生成完了と同時に 受注状態を「発注書送付済み」へ遷移させるコールバックも実装。
外部連携通知
notification.py
生産者への発注書送付ログ、購入者への発送通知文の組み立てを担当。
データベース設計
db.py
商品・送料マスタ、受注データの永続化と、 生産者別・月次の発注実績／コスト集計ロジックを担当。
テスト
tests / test_end_to_end.py
バックエンド6チーム全部を結線したE2E業務フロー（受注登録 → 発注書生成 → 状態遷移 → 発送通知 → 月次集計）と、各チームの単体テストを担当。
FRONTEND / INTEGRATION — UI構築と最終統合
バックエンド結合
app_full/main.py
6チームの部品を業務フローの順序で結線するエントリーポイントを構築し、 実機でE2E検証（受注登録〜月次集計が一気通貫で動くことを確認）。
フロントエンド（Web UI）構築
webapp/app.py, templates/
Flask + HTML/CSSでブラウザ操作画面を構築。日常の受発注操作画面に加え、 商品・送料・生産者マスタの登録／編集画面も実装。 既存のバックエンドロジックは書き換えず、関数呼び出しの形で組み込む設計。
最終統合・納品物作成
delivery/index.html, 利用ガイド, 本番投入手順書
バックエンド・フロントエンドを合わせて、自己完結型のデモ画面と 利用ガイド・本番投入手順書を作成。パイプライン内部の用語や役職名が 成果物に残っていないかを機械的に検証してから納品。
04 · QUALITY GATE · 差し戻し／エスカレーションの仕組み

各チームの成果物はレビューエージェントが実機でコマンドを実行して検証し、 承認 or 差し戻しを判定します。レビューの結果、既存チームの担当範囲を超える 追加処理が必要と判断された場合は、その場で新しいチームを編成して対応します。 差し戻しが3ラウンドを超えても解消しない場合は、 「誰の担当領域か」「なぜ直っていないか」を含む証跡（実行ログ・トレースバック・ タイムスタンプ比較）とともに自動で人間へエスカレーションする設計です。 統合工程では、既存成果物と重複する新規作成を避けるため、 grep等での実機検証を経てから「作らない」判断を下す場面もありました。

ROUND 1–3
レビュー・差し戻しサイクル
実行ログ・トレースバック・PASS/FAILの生ログを根拠に、 指摘事項を具体的なコード箇所付きで差し戻す。
ROUND 4 · ESCALATION
人間へのエスカレーション
3ラウンド解消しない指摘のみ、発見元・証跡・タイムスタンプ比較を添えて 人間の判断に回す。実際に1件発生した記録あり。
DELIVERY
納品物の言葉づかい検証
内部の役職名・運用用語が納品物（説明書・デモ画面）に 残っていないかをgrepで機械的に検証してから納品。
05 · FINAL REVIEW · 納品前レビューツールによる最終ゲート

パイプラインが生成した成果物は、最後に別途開発した納品前セキュリティ・品質検査ツール でレビューします。静的解析（Python: Ruff・mypy・Bandit／JavaScript・TypeScript: ESLint・tsc／ Java: Checkstyle・PMD）を行い、 「納品可能」「条件付き納品可能」「要修正」「判定不能」の4段階判定を根拠付きで返します。 ツール自体はDockerで隔離した環境での動的検査やAIによる意味レビューにも対応していますが、 現在のパイプラインで自動実行しているのは静的解析までです。動的検査と、セキュリティ専用の検査（秘密情報の検出・部品の脆弱性検査など）を組み込む作業を進めています。

納品可能
必須の静的・動的検査がすべて完了し、重大な指摘が無い状態。
条件付き納品可能
重大な指摘は無いが、検査範囲の一部が未実施（例：動的検査を実施していない）。 静的検査のみの標準構成では、正常時でもここまでが上限。
要修正
重大な指摘があり、納品前に修正が必要な状態。
判定不能
必須の検査自体が完了できなかった状態。「品質の合否」と「検査を完了できたか」を 別軸で扱う設計です。
// dev note このレビューツール自体も、設計・実装の各段階を担当外のAIによる独立レビューにかけ、 重大・中程度の指摘0件になるまで先に進めない、というAI開発パイプラインと同じ考え方で作りました。 Python／JavaScript・TypeScript／Javaに対応し、テストは450件以上が通過しています。

07 · DEV OPS

各チームの実装・レビュー・統合の判断根拠を、実行ログや差分の一次情報で 残す運用を徹底。設計統括エージェントは着手前に必ず既存の納品フォルダを確認し、 同一入力に対してすでに完了済みの成果物がないかを実機検証してから 作業に入る、という「重複作業を避けるチェック」を組み込んでいます。

納品物は「かんたん説明モード」「技術者向けモード」を ボタンで切り替えられる単一HTMLファイルとして自己完結させ、 クライアントが特別なソフトなしにブラウザだけで確認できる形にまとめました。

01 外から学ぶ

毎日、Hacker News・GitHub・ニュース・技術記事（Zenn）・公式の更新情報を集めています。週に1回は、論文データベース6か所（arXiv・Semantic Scholar・OpenAlex・Crossref・J-STAGE・CiNii）から、AIエージェントやRAGに関する論文も集めます。

集めた約3,000件は1つの表にまとめ、2段階でふるい分けます。1段目は生成AIではない判定モデルが明らかに不要なものを落とし、2段目でAIが優先度を付けます。優先度の高い候補はAIが中身を読み、「今の自分の環境と比べて何が良くなるか」を判定して日次のレポートにします。採用するかどうかは私が決め、採用したものは設計書を経て仕組みに組み込みます。

この調査は予備PCに切り分け、本体PCと2台で同時に処理しています。予備PCの4レーンで1時間に15〜21件。いまは、レーンを増やしたときにどこまで速くなるかを測りながら拡張しています。

02 内から学ぶ

パイプラインで起きた失敗は、すべて記録しています。一度起きた失敗は対処法として残し、同じことが起きればAIが人に聞かずに解消します（対処法27項目）。

さらに、失敗に種類を付けて数え、頻度と影響で「直すかどうか」を決める仕組みを段階的に入れています。1000回に1回の失敗は直さない。10〜20%起きる失敗は構造から直す。直した後は別の系統で本当に減ったかを確かめ、減っていなければ元に戻します。

最初の測定では、直近7日のレーンの強制停止783件（結果全体の32%）を種類別に分解しました。
